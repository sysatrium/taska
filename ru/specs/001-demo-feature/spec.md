## 1. Цель

Предоставить минимальную, хорошо специфицированную API-возможность, которая позволяет авторизованному клиенту обновлять статус существующей задачи с сохранением валидации, auditability и понятной обработки ошибок.

## 2. Бизнес-контекст

- Почему фича существует: task-centric системе нужен управляемый способ переводить работу между lifecycle-состояниями.
- Кто выигрывает: пользователи продукта, delivery-команды, интеграции и потребители отчётности.
- Что меняется при успехе: изменения состояния задач становятся явными, тестируемыми и contract-driven.
- Почему сейчас: это маленький вертикальный срез, подходящий как golden SDD example.

## 3. Карта оснований

### Подтверждённые факты

- Репозиторий организован вокруг Spec-Driven Development.
- Bootstrap и template rules требуют spec, plan, tasks и contracts до реализации.
- Фича намеренно спроектирована как демонстрационный артефакт.

### Выведенный контекст

- У сущности task, вероятно, есть поле lifecycle-статуса.
- Обновления статуса будут важны для downstream reporting и audit trails.
- API, вероятно, будет использоваться UI и будущими automation-клиентами.

### Рекомендуемые defaults

- Использовать выделенный endpoint для смены статуса, а не generic patch.
- Ограничить валидные статусы маленьким enum: `todo`, `in_progress`, `done`, `blocked`.
- Требовать reason при переводе задачи в `blocked`.

### Временные допущения

- Идентификаторы задач являются строковыми ID.
- Аутентификация основана на bearer-token.
- Первая версия не будет навязывать сложные role-based правила переходов.

### Требует подтверждения

- Нужно ли разрешать возврат из `done`.
- Нужна ли для blocked-задач структурированная taxonomy причин.
- Хранятся ли audit events синхронно или асинхронно.

## 4. Ожидаемые результаты

- Результат 1: авторизованный клиент может обновить статус существующей задачи через документированный API.
- Результат 2: невалидные переходы статуса отклоняются с явными validation errors.
- Результат 3: успешные изменения возвращают детерминированный response shape, пригодный для тестов и интеграций.

## 5. В скоупе

- Feature-level endpoint для смены статуса задачи.
- Валидация допустимых статусов и обязательных полей.
- Response contract и базовая обработка ошибок.
- Требования к audit event на уровне спецификации.

## 6. Вне скоупа

- Полные API создания и удаления задач.
- Массовые обновления.
- Сложные workflow engine или approval chains.
- Реальная доставка уведомлений.

## 7. Ограничения и допущения

### Ограничения

- Ограничения стека: оставаться technology-agnostic на уровне спецификации.
- Ограничения производительности: одно обновление статуса должно быть lightweight.
- Ограничения compliance или безопасности: только аутентифицированные вызовы могут выполнять обновления.
- Ограничения поставки: фича должна оставаться достаточно маленькой для demo pack.
- Ограничения интеграций: форма ответа должна быть достаточно стабильной для UI и automation use.

### Допущения

- Задача уже существует до вызова update.
- Базовая persistence уже существует где-то ещё в системе.
- Audit data можно минимально представить как кто, что и когда изменил.

## 8. Зависимости

- Upstream dependency: project-level определение сущности task.
- Downstream dependency: consumers отчётности или activity timeline.
- External dependency: механизм аутентификации.

## 9. Уже принятые решения

- Decision: обновление статуса публикуется как выделенный endpoint.
  - Status: Recommended
  - Rationale: упрощает ясность контракта и verification.
  - Implication: частичная мутация task намеренно ограничена.
  - Requires confirmation by: Engineering lead

- Decision: переходы в blocked требуют `blockedReason`.
  - Status: Provisional
  - Rationale: делает важные исключения явными.
  - Implication: клиенты должны передавать дополнительный контекст для blocked work.
  - Requires confirmation by: Product owner

## 10. Пограничные и отказные сценарии

- Пограничный сценарий: запрос повторяет текущий статус.
  - Ожидаемое поведение: вернуть успех без duplicate side effects или no-op response согласно утверждённому API design.
- Пограничный сценарий: переход в `blocked` без причины.
  - Ожидаемое поведение: отклонить с validation error.
- Отказной сценарий: task ID не существует.
  - Ожидаемое поведение: вернуть not found.
- Отказной сценарий: вызывающий не аутентифицирован.
  - Ожидаемое поведение: вернуть authentication error.

## 11. Критерии проверки

### Функциональная проверка

- Валидное обновление статуса возвращает ожидаемый response contract.
- Невалидное значение статуса отклоняется.
- Отсутствующий `blockedReason` отклоняется для `blocked` статуса.
- Неизвестный task ID возвращает not found.

### Нефункциональная проверка

- Поведение endpoint детерминировано.
- Примеры контракта валидны относительно JSON schema.
- Error responses остаются структурированными и стабильными.

### Наблюдаемость и диагностика

- логи: попытки обновления статуса и их результат.
- метрики: число успешных и неуспешных обновлений по причинам.
- трейсы: включать update operation в request tracing.
- алерты: опциональные позже для abnormal failure rates.

## 12. Первичные подсказки по задачам
