# taska RU

Русскоязычный production-grade набор для **Spec-Driven Development (SDD)** в greenfield-проектах.

Этот каталог предназначен для команд и специалистов, которые хотят вести разработку через спецификации, контракты и проверяемые артефакты **до** написания кода.

## Назначение

Используйте этот каталог, чтобы организовать цикл:

`Инициализация -> Спецификация -> Контракт -> План -> Задачи -> Реализация -> Проверка -> Обучение`

Подход ориентирован на:

- предсказуемую работу AI-агентов
- явные границы скоупа
- разработку через артефакты
- отдельную роль проверяющего агента
- обучение системы через инциденты и обновление спецификаций

## Политика каноничности

Корень репозитория является **каноническим источником** структуры и операционных правил.

Каталог `ru/` предназначен для:

- русскоязычного onboarding
- запуска bootstrap- и feature-процессов на русском языке
- локального human-facing использования в русскоязычной команде

Если между корнем и `ru/` появляется расхождение, сначала обновляется корневая документация, а затем синхронизируется `ru/`.

Терминологические правила см. в:

```text
ru/GLOSSARY.md
```

## Операционная модель

Этот набор рассчитан на запуск человеком:

1. Человек запускает шаги инициализации по порядку.
2. AI-агенты создают постоянные проектные артефакты.
3. Работа над фичами начинается только после прохождения входного контрольного рубежа.
4. Каждая фича реализуется через атомарные задачи.
5. Проверка выполняется отдельным проверяющим агентом.
6. Инциденты обновляют не только код, но и спецификации, ограничения и критерии проверки.

## Порядок инициализации

Запускайте файлы инициализации строго по порядку.

### 0.1 Создание конституции проекта

Файл:

```text

```

Выход:

```text
.specify/memory/constitution.md
```

### 0.2 Создание постоянного контекста агентов

Файл:

```text
ru/prompts/00-bootstrap/02-create-agents.md
```

```text
AGENTS.md

```

### 0.3 Создание проектного обзора

Файл:

```text

```

Выходы:

Файл:


## Порядок работы с фичей

Для каждой новой фичи создавайте отдельную папку:

```text
specs/001-feature-name/
  spec.md
  plan.md
  tasks.md
  research.md
  contracts/
    api-spec.yaml
    data-schema.json
```

Порядок прохождения жизненного цикла фичи:

1. `01-create-feature-spec.md`
2. `02-create-api-contract.md`
3. `03-create-plan.md`
4. `04-create-tasks.md`
5. `05-implement-task.md`
6. `06-verify-task.md`

## Этап сопровождения

Промпты сопровождения используются, когда реальность изменила исходный план:

1. `01-update-spec-after-incident.md`
2. `02-update-constitution.md`
3. `03-refine-tasks.md`
4. `04-run-pre-implementation-checklist.md`

Эти шаги не дают системе незаметно дрейфовать между замыслом, планом и реализацией.

## Обязательные условия перед кодингом

Писать код можно **только после** выполнения следующих условий:

- `constitution.md` существует и актуален
- `AGENTS.md` существует и актуален
- проектные обзорные артефакты созданы
- `spec.md` для фичи существует
- границы вне скоупа указаны явно
- API- и data-контракты созданы там, где это применимо
- `plan.md` создан
- `tasks.md` создан с зависимостями и шагами проверки

## Роли агентов

### Автор спецификации

Создаёт и обновляет спецификации и контракты.

### Архитектурный планировщик

Преобразует утверждённую спецификацию в архитектурный план, риски и схему вывода в эксплуатацию.

### Декомпозитор задач

Разбивает план на атомарные задачи с зависимостями и критериями приёмки.

### Реализатор

Реализует ровно одну задачу за раз.

### Проверяющий агент

Ищет нарушения скоупа, пропущенные пограничные сценарии, запрещённые паттерны и дефекты безопасности.

## Правила production-уровня

- Спецификации — первичные артефакты, код вторичен.
- Нельзя реализовывать фичу из расплывчатого запроса.
- В `tasks.md` нельзя оставлять многодневные задачи.
- Нельзя скрывать допущения; неразрешённые вопросы должны жить в разделе открытых вопросов.
- Нельзя полагаться только на самопроверку.
- Каждый production incident должен обновлять спецификации, ограничения или критерии проверки.
- Сначала обновляется корневая документация, затем русская локализация.

## Быстрый старт

1. Пройдите этап `00-bootstrap`.
2. Просмотрите созданные артефакты человеком.
3. Зафиксируйте конституцию и правила агентов.
4. Создайте `specs/001-first-feature/`.
5. Пройдите жизненный цикл фичи.
6. Запустите контрольный список перед началом кодинга.
7. Выполняйте слияние только после устранения замечаний проверяющего агента.
