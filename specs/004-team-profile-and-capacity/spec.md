## Цель

Эта фича вводит глобальный профиль команды, независимый от planning period, который затем используется в последующих сценариях планирования.
Она позволяет Head of Product или Team Lead создать и поддерживать команду, выбрать её компетенции из централизованного справочника и сохранить команду как переиспользуемую сущность для planning-сценариев.
Цель фичи — сделать команду явным участником planning-системы до начала period-specific заполнения capacity, привязки planning items и анализа перегрузки.

## Пользовательский сценарий

Основной end-to-end сценарий:

1. Head of Product или Team Lead открывает сценарий создания команды.
2. Пользователь создаёт глобальный профиль команды с базовыми данными.
3. Пользователь выбирает релевантные компетенции из централизованного справочника.
4. Пользователь сохраняет команду как глобальный профиль команды.
5. Система позволяет использовать эту команду в следующих фичах, где для конкретного planning period будет задаваться period-specific capacity profile.

## Ожидаемые результаты

- В системе можно создать глобальный профиль команды, пригодный для дальнейших planning-сценариев.
- У команды есть явный и нормализованный набор компетенций из централизованного справочника.
- Глобальный профиль команды отделён от period-specific capacity данных.
- Система получает переиспользуемую сущность команды для следующих planning-шагов.

## Что проверяем / гипотезы

### Confirmed

- Продукт предназначен для планирования одного продукта или product line с участием 10–15 команд.
- Система должна учитывать capacity по компетенциям.
- Team Lead должен иметь возможность указывать capacity команды по компетенциям.
- Team object является глобальной сущностью.
- Team object могут создавать и Head of Product, и Team Lead.
- Участие команды в конкретном периоде подтверждается через наличие planning items, а не через отдельный флаг участия.
- Компетенции выбираются из централизованного справочника.
- Capacity может указываться на уровне планируемого периода и/или итерации.
- Подсветка неполноты capacity относится к planning progress по командам внутри периода.

### Inferred

- Глобальная сущность команды должна существовать до того, как planning items начнут стабильно привязываться к командам.
- Period-specific capacity profile не должен смешиваться с глобальным профилем команды.
- Централизованный справочник компетенций уменьшит число дублей и расхождений в vocabulary между командами.

### Approved decisions reflected in this spec

- Capacity в MVP измеряется в человеко-днях (downstream product decision для следующих features).
- Period-specific capacity profile не входит в feature 004.
- Локальное расширение справочника компетенций пользователями не входит в MVP этой фичи.
- Минимальный набор полей для создания команды достаточен: название команды, владелец профиля команды или ответственная роль, хотя бы одна компетенция.
- Справочник компетенций предзаполнен типовым набором; администрирование справочника не входит в feature 004.
- Типовой набор компетенций для MVP включает: Backend Development, Frontend Development, QA / Testing, DevOps / Infrastructure, Design (UI/UX), Product Management, Data Engineering, Mobile Development, Security / InfoSec.

### Provisional default

- Новая команда создаётся без отдельной связи с planning period.
- Period-specific capacity вводится в следующей feature, а не в рамках 004.
- В рамках feature 004 компетенции можно свободно изменять и удалять (поведение при наличии downstream-связей будет определено в следующих features).

### Открытые вопросы для следующих фич

- Как должна вести себя система при попытке изменить или удалить компетенцию у команды после появления planning items, привязанных к этой компетенции? (Отложено до feature planning-items)

## В скоупе

- Создание глобального профиля команды.
- Редактирование базовых данных команды, значимых для planning.
- Выбор компетенций из централизованного справочника.
- Сохранение команды как глобального профиля команды.
- Подготовка глобального профиля команды для следующих фич, где будут задаваться period-specific capacity и planning items.

## Вне скоупа

- Ввод и обновление capacity по компетенциям.
- Хранение capacity в человеко-днях для конкретного planning period.
- Явный флаг участия команды в конкретном planning period.
- Создание planning items.
- Распределение работы по итерациям.
- Анализ перегрузки, конфликтов приоритетов и расчёт того, что не помещается в период.
- Локальное или свободное расширение справочника компетенций пользователями в MVP.
- Администрирование централизованного справочника компетенций.

## Ограничения

- Фича должна оставаться небольшим пользовательским вертикальным срезом и не включать downstream planning logic.
- Спецификация не должна уходить в детали реализации UI, API или storage-модели раньше времени.
- MVP не должен зависеть от обязательных внешних интеграций.
- Правила ролей пока ограничены подтверждённым минимумом: team object могут создавать Head of Product и Team Lead.
- Capacity как planning-данные периода не должен храниться в глобальном профиле команды.
- Справочник компетенций предзаполнен типовым набором; расширение справочника не входит в MVP.

## Уже принятые решения

- Решение: Team object является глобальной сущностью.
  - Status: Approved
  - Rationale: команда должна переиспользоваться в разных planning-контекстах.
  - Implication: участие в периоде и period-specific capacity нельзя моделировать как часть базового профиля команды.

- Решение: Team object могут создавать и Head of Product, и Team Lead.
  - Status: Approved
  - Rationale: обе роли участвуют в planning flow и не должны быть заблокированы на старте.
  - Implication: permission model должен допускать обе роли в рамках этой feature.

- Решение: Компетенции выбираются из централизованного справочника.
  - Status: Approved
  - Rationale: это снижает расхождения в vocabulary и делает planning-модель более управляемой.
  - Implication: в MVP пользователи не добавляют новые компетенции локально.

- Решение: Capacity в MVP измеряется в человеко-днях.
  - Status: Approved
  - Rationale: это продуктовое решение верхнего уровня для downstream planning features.
  - Implication: downstream features и контракты должны использовать человеко-дни как базовую единицу capacity.

- Решение: Участие команды в периоде подтверждается через planning items.
  - Status: Approved
  - Rationale: это отделяет глобальную сущность команды от периодного planning state.
  - Implication: в этой фиче не должно быть явного механизма "подключить команду к периоду".

- Решение: Period-specific capacity profile не входит в feature 004.
  - Status: Approved
  - Rationale: capacity зависит от планируемого периода и не является стабильной частью глобального профиля команды.
  - Implication: работа с capacity должна быть вынесена в следующую feature.

- Решение: Минимальный набор полей для создания команды достаточен.
  - Status: Approved
  - Rationale: дополнительные поля не обязательны для MVP; минимум — название команды, владелец профиля или ответственная роль, хотя бы одна компетенция.
  - Implication: API контракт не должен требовать дополнительных обязательных полей.

- Решение: Справочник компетенций предзаполнен типовым набором; администрирование не входит в feature 004.
  - Status: Approved
  - Rationale: это упрощает MVP и снимает риск блокировки на старте из-за пустого справочника.
  - Implication: в feature 004 нет admin-сценариев управления справочником; типовой набор должен быть определён до начала реализации.

- Решение: Типовой набор компетенций для MVP фиксируется заранее.
  - Status: Approved
  - Rationale: явный seed list убирает неоднозначность на этапе API contract и реализации.
  - Implication: при инициализации системы справочник должен быть предзаполнен как минимум следующими компетенциями: Backend Development, Frontend Development, QA / Testing, DevOps / Infrastructure, Design (UI/UX), Product Management, Data Engineering, Mobile Development, Security / InfoSec.

- Решение: В рамках feature 004 компетенции можно свободно изменять и удалять.
  - Status: Approved (provisional)
  - Rationale: feature 004 не создаёт downstream-связей; поведение при наличии связей будет определено в следующих features, когда появятся planning items.
  - Implication: API контракт feature 004 не должен включать validation для защиты downstream-связей.

## Edge cases and failure scenarios

- Edge case: Head of Product и Team Lead почти одновременно создают одну и ту же команду.
  - Expected behavior: система предотвращает очевидный дубль или предлагает использовать уже существующую команду.

- Edge case: пользователь пытается сохранить команду без выбранных компетенций.
  - Expected behavior: система не считает профиль завершённым и явно показывает, что профиль компетенций неполный.

- Edge case: пользователь без подтверждённой роли пытается создать команду.
  - Expected behavior: система не допускает создание team object и показывает, что действие недоступно для текущей роли.

- Edge case: централизованный справочник не содержит нужной компетенции.
  - Expected behavior: система не подменяет её локальным значением в MVP и показывает, что требуется обновление централизованного справочника (вне scope feature 004).

- Edge case: команда уже создана и затем переименовывается.
  - Expected behavior: система позволяет изменить отображаемое имя команды без разрушения её стабильной identity и downstream-связей.

- Edge case: команда существует как глобальная сущность, но пользователь ожидает, что она уже участвует в конкретном planning period.
  - Expected behavior: система явно разделяет глобальный профиль команды и period-specific planning context и не считает команду автоматически включённой в период.

- Failure scenario: пользователь пытается удалить компетенцию в рамках feature 004.
  - Expected behavior: система позволяет удалить компетенцию, потому что downstream-связи ещё не созданы.

- Failure scenario: два пользователя одновременно изменяют профиль одной команды.
  - Expected behavior: система не теряет изменения молча и требует разрешить конфликт.

- Empty or no-data state: в системе ещё нет ни одной команды.
  - Expected behavior: система показывает пустое состояние с явным CTA на создание первой команды.

- Empty or no-data state: централизованный справочник пуст или не содержит релевантных компетенций.
  - Expected behavior: система явно показывает, что команда не может быть полноценно настроена до пополнения справочника (вне scope feature 004).

- Loading state:
  - Expected behavior: при загрузке команды и справочника компетенций система показывает предсказуемое loading state без частично сломанной формы.

- Error state:
  - Expected behavior: если не удалось загрузить или сохранить профиль команды, система сохраняет пользовательский контекст и показывает понятную ошибку без потери уже введённых данных.

## Критерии проверки

### AC01 — Создание команды Head of Product

Given пользователь с ролью Head of Product открывает сценарий создания команды  
When он заполняет обязательные поля команды и сохраняет форму  
Then система создаёт глобальный профиль команды

### AC02 — Создание команды Team Lead

Given пользователь с ролью Team Lead открывает сценарий создания команды  
When он заполняет обязательные поля команды и сохраняет форму  
Then система создаёт глобальный профиль команды

### AC03 — Выбор компетенций из централизованного справочника

Given пользователь создаёт или редактирует профиль команды  
When он выбирает компетенции  
Then система позволяет выбрать компетенции только из централизованного справочника

### AC04 — Сохранение глобального профиля команды без period-specific capacity

Given пользователь создал профиль команды и выбрал компетенции  
When он сохраняет команду  
Then система сохраняет глобальный профиль команды без требования заполнить capacity для конкретного периода

### AC05 — Отсутствие period-specific capacity в рамках feature 004

Given пользователь работает в рамках feature 004 team-profile-and-capacity  
When он создаёт или редактирует команду  
Then система не требует и не сохраняет period-specific capacity profile

### AC06 — Отсутствие отдельного флага участия в периоде

Given пользователь создаёт или редактирует глобальный профиль команды  
When он работает с данными команды  
Then система не требует и не сохраняет отдельный флаг участия команды в planning period в рамках этой фичи

### AC07 — Отсутствие сценариев planning items в рамках фичи

Given пользователь работает в рамках feature 004 team-profile-and-capacity  
When он завершает все доступные сценарии этой фичи  
Then система не создаёт planning items  
And не включает распределение по итерациям  
And не выполняет анализ перегрузки

### AC08 — Переиспользование команды в следующих фичах

Given глобальный профиль команды сохранён  
When downstream planning feature обращается к доступным командам  
Then команда может быть выбрана и использована как существующий глобальный профиль команды для дальнейших planning-сценариев

### AC09 — Свободное изменение компетенций в рамках feature 004

Given пользователь редактирует глобальный профиль команды в рамках feature 004  
When он изменяет или удаляет компетенцию  
Then система позволяет это сделать без дополнительных ограничений, потому что downstream-связи ещё не созданы
